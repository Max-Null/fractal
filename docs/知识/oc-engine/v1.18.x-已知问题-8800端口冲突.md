# v1.18.x 已知问题：v2 server 端口 8800 冲突

> 锚点：serve 1.18.15（2026-08-09 实测定案）

## 事实

- serve 1.18.15 启动时会额外启动一个 **v2 server**（默认端口 **8800**），与 `--port` 指定的 v1 API 端口相互独立
- **任何 opencode 客户端**（官方桌面端、TUI、其他 serve）都会占用 8800——多个客户端并存时后启动者 v2 server 失败
- 失败特征（stderr）：`Failed to start server. Is port 8800 in use?`（**非致命**——serve 主体继续运行）
- **v2 路由（/api/*）在 v1 端口同时存在**（实测 /api/model 在分形端口返回 401 = 路由存在）——分形 compact 已走 v1 端口 v2 路由，功能不受 8800 冲突影响

## 影响面

| 场景 | v2 server（8800） | v1 API（--port） | 分形功能 |
|------|------------------|------------------|---------|
| 8800 空闲 | ✅ 正常 | ✅ 正常 | 全部 |
| 8800 被占 | ❌ 启动失败（报错） | ✅ 正常 | **全部正常**（降噪提示） |

## 分形处理（e3e3a91）

- stderr 匹配 `/Failed to start server\. Is port \d+ in use/` → 控制台提示一次：「检测到 8800 端口被占用（通常为 OpenCode 官方桌面端）——serve 的 v2 API 服务不可用；分形使用 v1 API，功能不受影响」（`v2ConflictHinted` 模块级跨重试一次）
- serve.log 保留原始报错
- 8800 冲突**不重试不阻断**（v1 正常即可）

## 排除项（实测）

- `OPENCODE_PORT` env：1.x 源码中不存在此变量（注入无效）
- `--port 0`（随机 v1 端口）不影响 v2 server 的 8800

## 未来根治（候选）

**OpenCode 2.0（beta 线）**：Node 化重写——引擎可进程内嵌入（端口自控），8800 冲突消失。1.x 的 `createOpencodeServer`（SDK）只是 spawn 二进制的封装（OpenChamber 即此用法，同样有 8800 行为）。2.0 稳定后分形迁移候选（D2 补充）。
